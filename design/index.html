Problem and Goal

the upstream Claude-Code-Game-Studios source snapshot is a Claude Code framework with Claude-specific agents, slash-command skills, hooks, settings, and CLAUDE.md include conventions. Codex cannot consume those files directly as a native plugin or repository instruction set. This port defines a Codex-native package that preserves the game-studio workflow while replacing Claude-specific surfaces with Codex skills, plugin metadata, repository instructions, references, scripts, and validation gates.

The goal is a reviewable migration target that can be implemented without guessing file locations, conversion rules, or completion criteria.

Scope and Non-Goals

In Scope

  • Define a Codex plugin package for the reusable Game Studios workflow.
  • Map 73 Claude skills into Codex SKILL.md folders with Codex trigger descriptions and progressive-disclosure references.
  • Preserve 49 role prompts as Codex role references and route them through skills or implementation guidance.
  • Translate root and path-scoped Claude instructions into Codex AGENTS.md and plugin references.
  • Carry hook scripts forward as explicit validation scripts, with Codex hook registration gated by verified Codex hook schema support.
  • Define validation checks for manifest shape, skill metadata, migrated links, and removed Claude-only assumptions.

Out of Scope

  • Changing the game-development methodology, studio hierarchy, or workflow phase model.
  • Rewriting game design templates for a different design framework.
  • Implementing a new Codex runtime, MCP server, or external app integration.
  • Claiming Claude-style custom subagents exist in Codex unless the current Codex product exposes a matching local extension contract.
  • Shipping converted files to CODEX_HOME; this spec targets a repo-local plugin first.

System Boundaries

The source tree is read-only reference material. The generated Codex package owns converted plugin files and repository-local instructions. Runtime game projects consume the package after installation or local marketplace registration.

Ownership and Source of Truth

Layer Owns Rebuildable
the upstream Claude-Code-Game-Studios source snapshot Original Claude content and upstream license context. No. Treat as external reference input.
design/ Porting design, conversion contracts, validation plan, and implementation tracker. No. This is the canonical spec package.
plugins/codex-game-studios Codex-native plugin manifest, skills, references, scripts, and assets created by the port. Yes, from reference input plus conversion scripts, after manual review of role and skill wording.
AGENTS.md Repository-local Codex instructions for projects that use this template directly. Partially. Boilerplate is generated; project-specific edits are user-owned.
.agents/plugins/marketplace.json Local marketplace ordering and install policy for the repo-local plugin. Yes. Recreated from plugin name, path, category, and policy.

Core Decisions

What: The Codex deliverable is a repo-local plugin at plugins/codex-game-studios plus a root AGENTS.md for repository instructions.

Why: The reusable workflow belongs in a plugin, while repository behavior and path rules must be visible to Codex through local instructions. Reversal condition: If the user wants a home-wide installation package, use ~/plugins/codex-game-studios and ~/.agents/plugins/marketplace.json instead.

What: Claude slash commands become Codex skills with trigger descriptions; command names remain as aliases inside descriptions and examples.

Why: Codex skill routing uses name and description metadata, while Claude slash command invocation is a source convention. Reversal condition: If Codex adds slash-command compatibility for local skills, add generated command shims without changing the canonical skill bodies.

What: Claude agents become role reference files and routing tables, with optional skill-level instructions for when Codex should use built-in sub-agent tools.

Why: The available Codex extension surfaces do not show a Claude-compatible custom agent registry with per-agent model, tool, and memory metadata. Reversal condition: If a Codex custom-agent schema is available in the target environment, add a companion generated agent package after validating that schema.

What: Claude hook scripts are preserved as scripts first; automatic hook registration is a later phase that requires a verified Codex hook JSON contract.

Why: The plugin manifest supports a hook path, but this repository does not contain the Codex hook event schema. Reversal condition: Once the Codex hook schema is confirmed, generate hooks.json and wire compatible scripts.

What: Source references using Claude @path include syntax must be resolved into explicit Codex instructions or normal Markdown links.

Why: The port must not rely on unverified include expansion. Reversal condition: If Codex documents compatible include semantics for AGENTS.md, the generated instructions may keep includes where rendering and loading are tested.

Failure Cases and Acceptance

Capability Failure Case Acceptance Signal
Plugin manifest Missing required manifest fields or non-relative component paths. .codex-plugin/plugin.json validates as JSON and includes name, version, description, skills, and interface.
Skill routing A converted skill lacks name or a Codex-readable trigger description. All 73 source skills have generated Codex skill folders with valid frontmatter and no Claude-only tool allowlists.
Role preservation Agent authority, escalation paths, or domain boundaries are dropped during conversion. All 49 source agents have role reference files and are listed in the role routing index.
Claude-only syntax removal Generated Codex files still instruct users to rely on .claude, CLAUDE.md, Task, AskUserQuestion, or slash commands as the only invocation path. Search results for Claude-only constructs are either zero in generated runtime files or documented in source-reference sections only.
Hook behavior Automatic hook registration is generated against an unverified event schema. Initial port exposes hook scripts as manual validation scripts; hook registration remains blocked until schema verification passes.

Implementation Phases

  1. Phase 1: Inventory and license boundary. Goal: produce a source manifest for agents, skills, hooks, rules, docs, templates, and license-bearing files. Includes file counts, source hashes, and excluded paths such as .git. Verify: manifest count matches 49 agents, 73 skills, 12 hooks, and 11 rules.
  2. Phase 2: Plugin scaffold. Goal: create the Codex plugin shell. Includes .codex-plugin/plugin.json, skills/, references/, scripts/, and optional marketplace entry. Verify: JSON files parse and paths are relative to plugin root.
  3. Phase 3: Skill and role conversion. Goal: convert workflow behavior into Codex-native skills and references. Includes frontmatter normalization, Claude tool removal, role routing index, and progressive-disclosure reference links. Verify: every source skill and agent has exactly one generated target entry.
  4. Phase 4: Repository instructions and validation scripts. Goal: translate root instruction behavior and portable hooks. Includes root AGENTS.md, path guidance, validation scripts, and hook-registration decision record. Verify: generated instructions contain no unresolved @path includes.
  5. Phase 5: Review and trial run. Goal: prove the port supports a representative Game Studios workflow. Includes running a sample concept-to-GDD path, a code-review path, and validation checks. Verify: reviewer can follow the workflow without opening the upstream Claude-Code-Game-Studios source snapshot.
